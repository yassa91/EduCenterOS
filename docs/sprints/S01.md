## 1. الهدف والنتيجة العملية

تأسيس Backend قابلة للتشغيل والتطوير: المشروع موجود على GitHub، يستعيد الحزم ويتبني ويعمل محليًا، PostgreSQL متاحة للتطوير والاختبارات، وتعمل الفحوصات تلقائيًا على Pull Requests.

عند اكتمال السبرنت يستطيع مطور تشغيل المشروع من نسخة جديدة باتباع README، وتشغيل الاختبارات دون حساب Infisical أو أسرار تطوير حقيقية. API التشغيل المحلية التي تحتاج أسرارًا حقيقية تستخدم المسار المعتمد في T36/T37.

## 2. النطاق

داخل السبرنت:

- القرارات المطلوبة للتشغيل المحلي والـLogging والـCI.
- تهيئة Git/GitHub ودورة Branch/PR/Review/Merge.
- SDK وSolution وAPI Host وإدارة الحزم والإعدادات المشتركة.
- إعدادات التشغيل، Logging آمنة، Correlation ID، وفحوصات التشغيل والجاهزية.
- PostgreSQL 18 محلية ومسار أسرار التطوير وبيئة اختبار معزولة.
- اختبارات السلوك المنفذ وقواعد الهيكل المنطبقة، وCI وتعليمات التشغيل.

مؤجل:

- تسجيل الدخول والحسابات والصلاحيات والـBusiness Modules.
- إنشاء المؤسسة والطلاب والمجموعات والعمليات المالية.
- Frontend وMarketplace وProduction deployment.
- Events/Outbox/jobs ومزودو الإشعارات والمدفوعات.

الموديولات وجداولها وMigrations تنشأ مع أول Feature تحتاجها وفق T04/T08. لا ننشئ schemas مستقبلية أو BuildingBlocks فارغة لمجرد إكمال هيكل شكلي. لا ننفذ JWT أو key rings أو Data Protection persistence قبل وجود Feature تستخدمها.

**المراجع:** T01/T04/T07/T08/T31/T32/T33/T35/T36/T40.

**معايير القبول:**

1. ملفات T34/T37/T38 موجودة ومحددة الحالة والنطاق والملكية.

**التحقق:** مراجعة تناسق القرارات والمراجع والعقود، وتسجيل inventory البيئة دون عرض أسرار. حفظ التسليم ضمن bootstrap baseline في T02.

## 5. S01-T02 — Git وGitHub

**المحتوى:** التأكد من الوجهة وملكيتها وحالتها، تهيئة أو ربط المستودع دون الكتابة فوق تاريخ موجود، initial commit، `.gitignore` وPR template وإعداد Squash Merge وقواعد `main` المتاحة.

**معايير القبول:**

1. المستودع المحلي متصل بوجهة GitHub الصحيحة و`main` متزامنة معها.
2. ملفات Business/Technical والسبرنت محفوظة، دون Secrets أو `.DS_Store` أو outputs مؤقتة.
3. Squash Merge متاحة، ونموذج PR يطلب Task ID وهدف التغيير ونتائج التحقق.
4. تسجل قواعد الحماية المفعلة فعليًا وأي قيد في صلاحيات/خطة GitHub. لا ندعي enforcement غير متاحة.
5. Required CI check لا تفعّل باسم غير موجود قبل تجهيزها وإثبات تشغيلها في T06؛ قواعد العمل تظل ملزمة وفق T40.

**التحقق:** فحص remote والتاريخ والملفات المتتبعة والإعدادات الفعلية. الBootstrap تسبق دورة PR، ثم تغييرات هذه التاسك التي تلي bootstrap تمر عبر PR حسب T40.

## 6. S01-T03 — Solution وSDK والحزم

**الهدف:** أساس .NET موحد يبنى محليًا وفي CI.

**المحتوى:** Solution و`EduCenterOS.Api`، `global.json` و`Directory.Build.props` و`Directory.Packages.props`، واختيار stable SDK/packages متوافقة. المشاريع والمكتبات الإضافية تنشأ لحاجة فعلية فقط.

**معايير القبول:**

1. SDK محددة وفق T01؛ `net10.0` وNullable وImplicitUsings مضبوطة.
2. الحزم المباشرة محددة مركزيًا؛ لا Preview أو floating versions.
3. Restore وRelease Build ينجحان من checkout نظيفة.
4. Host لا تحتوي Business rules أو بيانات أو موديولات مستقبلية.

**التحقق:** restore/build على SDK المثبتة ومراجعة هيكل المشاريع ونسخ الحزم.

## 7. S01-T04 — API Host

**الهدف:** Host تعمل بعقود إعداد وتشغيل قابلة للاختبار.

**المحتوى:** Composition Root واضحة، environment validation، typed options للوظائف النشطة، correlation/logging، exception handling المنطبق، operational liveness/readiness وفق T34، وتوليد OpenAPI وفق T31 عند الحاجة.

**معايير القبول:**

1. البيئة مطلوبة وصحيحة؛ missing/unknown/conflicting environment تفشل وفق T36.
2. الإعدادات المطلوبة للوظائف النشطة تتحقق قبل قبول الخدمة كجاهزة.
3. Health تعرض حالة مختصرة؛ endpoints التشغيل خارج `/api/v1` والـpublic OpenAPI وفق T31/T34.
4. Correlation ID والعقود المنطبقة من T31/T32 تعمل، والـLogging لا تعرض secrets أو request bodies أو headers حساسة.
5. أخطاء التطبيق غير المتوقعة لا تكشف stack traces أو connection strings إلى الـClient.
6. Health في هذه التاسك تثبت حالة الـHost فقط؛ فحص DB يضاف في T05، ولا تدعي الجاهزية اعتمادًا لم ينفذ بعد.

**التحقق:** تشغيل محلي وHTTP checks، ثم تثبيت سيناريوهات النجاح والفشل في IntegrationTests ضمن T06. لا public demo Business endpoint لتبرير بنية مبكرة.

## 8. S01-T05 — PostgreSQL والأسرار وعزل الاختبارات

**الهدف:** اعتماد تشغيل حقيقي للتطوير، وDB اختبار disposable منفصلة وآمنة.

**المحتوى:** PostgreSQL 18 عبر Docker Compose للتطوير، loopback binding وتخزين مناسب لإصدارها، Infisical dev bootstrap وفق T36/T37، وtest-owned PostgreSQL provisioning مع synthetic credentials وfail-closed ownership guard.

**معايير القبول:**

1. API المحلية تتصل بقاعدة التطوير عبر المسار الصريح المعتمد للأسرار.
2. بيانات PostgreSQL المحلية تبقى بعد restart؛ لا schema/DbContext لموديول غير نشطة.
3. readiness تعكس DB outage، مع بقاء liveness مستقلة عنها.
4. الاختبارات تحصل على disposable DB خاصة بكل run/worker، دون dev/Infisical/Production fallback.
5. أي migration/reset/drop تختبر actual identity وملكية قاعدة الاختبار وفق T33 قبل effects؛ رفض الوجهة غير المملوكة يثبت دون تعريض dev DB لحذف حقيقي.
6. لا Secrets في Git أو raw command arguments أو logs؛ Testing لا تستدعي Infisical.
7. التشغيل الحقيقي لـInfisical يثبت بعد توفير project/endpoint/path وdeveloper access؛ missing access تسجل كاعتمادية ولا يعوضها fallback صامت.

**التحقق:** اتصال حقيقي، restart/persistence، DB outage/readiness، isolation/ownership negative checks، وbootstrap validation. لا تدعى اختبارات Migrations لم توجد بعد.

## 9. S01-T06 — الاختبارات والـCI وتعليمات التشغيل

**الهدف:** أدلة تحقق قابلة للتكرار محليًا وعلى GitHub، وتعليمات تشغيل من نسخة جديدة.

**المحتوى:** xUnit v3/VSTest حسب T33؛ Unit للسلوك المستقل الموجود، Integration للـHost وDB، Architecture للقواعد المنطبقة؛ GitHub Actions حسب T38؛ README للتشغيل والفحص والتشخيص.

**معايير القبول:**

1. test discovery والتنفيذ يعملان بالrunner المحددة؛ لا empty/pass-only tests أو skip لفحص مطلوب.
2. اختبارات البيئة والـconfiguration والـHTTP والـhealth والـlogging/عدم التسريب تغطي السلوك الذي نفذ فعليًا.
3. اختبارات PostgreSQL تعمل على PostgreSQL 18 حقيقية وتثبت عزل DB ورفض cleanup خارج ملكية fixture.
4. CI تعمل على PR و`main` دون أسرار تشغيل حقيقية أو وصول Infisical، وتحتفظ بنتائج تحقق آمنة.
5. workflow تفشل عند build/test failure؛ Required Check تفعّل بعد إثبات اسمها وتشغيلها وفق الإمكانات المتاحة.
6. README تكفي لتجهيز نسخة جديدة وتشغيلها واختبارها، وتفصل متطلبات dev الحقيقي عن automated tests.
7. سجلات التسليم ومراجعة السبرنت تعكس النتائج الفعلية، مع تسجيل أي قيد منع تحققًا مطلوبًا.

**التحقق:** الفحوصات المحلية المطلوبة، GitHub Actions run فعلية على PR، واتباع README من checkout جديدة مع الاعتماديات المذكورة.
