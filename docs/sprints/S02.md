## 1. الهدف والنتيجة العملية

تنفيذ أول Business Feature كاملة داخل `IdentityAccess`: إنشاء حساب جديد لشخص جديد بعد توثيق رقم الموبايل، فوق Host منظمة وBuildingBlocks صغيرة مستخدمة فعلًا.

عند اكتمال السبرنت يستطيع المطور من خلال الـAPI:

1. طلب كود لتوثيق رقم موبايل مصري، وإعادة طلبه وفق الحدود المعتمدة.
2. التحقق من الكود والحصول على إثبات مؤقت لتوثيق الرقم.
3. إرسال الاسم وكلمة المرور والبريد الاختياري مع الإثبات.
4. إنشاء `PersonIdentity` و`UserAccount` واستهلاك الإثبات في Transaction واحدة على PostgreSQL الحقيقية.
5. التأكد من أن الرقم موثق، وكلمة المرور محفوظة كبصمة، وأن الطلبات المتزامنة لا تنشئ حسابين ولا تعيد استهلاك الإثبات.

إنشاء الحساب **لا يسجل الدخول**: لا `UserSession` ولا Access JWT ولا Refresh Credential ضمن هذا المسار. الحساب لا يمنح Role أو Permission أو Membership، ولا ينشئ مؤسسة أو ملف طالب أو علاقة ولي أمر.

النتيجة المستهدفة للتطوير والاختبارات، وليست إطلاقًا إلى Production أو وعدًا بتسليم SMS حقيقية. وسيلة استلام كود التطوير تكون آمنة ومحدودة بالبيئة المحلية؛ الاختبارات تستخدم adapter منفصلة. التكامل مع مزود SMS حقيقي يتطلب اتفاقًا وتجهيزًا لاحقين.

## 4. الفلو المتفق عليه

```text
RequestPhoneVerification
  → validate and normalize phone
  → apply issue/resend/abuse budgets
  → invalidate older active challenge for the same purpose/target
  → create registration challenge and store OTP HMAC + key version
  → deliver code through the selected environment-owned adapter

VerifyPhone
  → validate challenge/code/purpose/expiry/attempts/current state
  → increment failed attempts atomically when verification fails
  → mark verified once and generate a short-lived high-entropy proof
  → store proof hash and return raw proof once

RegisterAccount
  → validate proof/challenge/purpose/expiry and submitted basic data
  → obtain the phone from the verified challenge, not a client replacement
  → enforce normalized phone/email uniqueness
  → generate separate UUID v7 IDs and hash the password
  → create PersonIdentity + UserAccount + consume proof
  → commit one transaction
  → return the agreed safe registration response, without login credentials
```

### قواعد الفلو

- الرقم المحلي والصيغة الدولية المكافئة يصلان لنفس القيمة canonical؛ لا يسمح اختلاف الكتابة بإنشاء حسابين.
- Purpose التسجيل تحددها الـUse Case (`RegisterAccount`)، وليس generic purpose يختارها الـClient.
- Challenge واحدة قابلة للاستخدام لكل Purpose + NormalizedTarget وفق T12. إصدار كود جديد يبطل القديم، ولا يعيد rolling budgets إلى الصفر.
- ردود request/resend والتحقق والفشل تراعي anti-enumeration؛ لا يحدد HTTP/body/timing مسارًا متعمدًا لكشف وجود حساب.
- OTP عشوائية من CSPRNG دون modulo bias؛ تخزن HMAC مرتبطة بـchallenge/purpose/target مع `HashKeyVersion` ومقارنة constant-time.
- VerificationProof عالية الـentropy وفق T12، قصيرة العمر ومرتبطة بالـchallenge/purpose/target؛ تحفظ بصمتها فقط، ولا توضع في URL أو query أو logs.
- `nowUtc >= ExpiresAtUtc` يعني Expired. الـHandler تقرأ `IClock.UtcNow` مرة للعملية وتمرر الزمن للـDomain.
- التحقق الناجح مرة واحدة، واستهلاك الإثبات مرة واحدة؛ التنفيذ المتزامن لا يخلق proof ثانية أو حسابًا موازيًا.
- التحقق من صحة البيانات قبل التسجيل لا يستهلك الإثبات وحده. فشل العملية قبل Commit يتراجع معه إنشاء الحساب/الشخص واستهلاك الإثبات.
- unique/check/FK constraints هي آخر خط دفاع بجانب Domain/Application validation؛ pre-check وحدها لا تحمي التسابق.
- أخطاء Provider/DB والـcancellation لا تزور Business outcome. لا blind retries لعملية أمنية أو Commit غير معلوم وفق T16/T17/T32.
- بيانات الحساب الجديد حسب T12: `Status = Active`، `SecurityVersion = 1`، `AccessFailedCount = 0`، `InitialOnboardingIntent = null`، مع phone verification timestamp.
- البريد الاختياري normalized وunique عند وجوده حتى قبل Verification؛ `EmailVerifiedAtUtc` تظل غير مثبتة ولا يمنح البريد صلاحية Login.
- PersonIdentity جديدة لهذا المسار، وUserAccount مرتبطة بها بـFK وNOT NULL وUNIQUE؛ لا linking تلقائي بالاسم أو contact.

### صندوق رسائل التطوير المعتمد

تسلم `DevelopmentOtpSender` الكود إلى `.local/otp/<challengeId>.json` محليًا. رد طلب الكود يحمل `challengeId` فقط مع المواعيد؛ يقرأ المطور الرسالة من الملف ويقدم الكود لنفس Verify API المستخدمة فعليًا. لا إرسال SMS حقيقي ولا endpoint لقراءة الكود.

الملف **رسالة تسليم مؤقتة** في Development وليس تخزين credential داخل قاعدة البيانات؛ OTP في `otp_challenges` تظل HMAC فقط. هذا استثناء تسليم تطوير صريح معتمد، ولا يجيز حفظ الأكواد في logs أو snapshots أو artifacts أو أي بيئة أخرى. المجلد 0700 والملف 0600، خارج Git، بدون symlinks، ومربوط بعمر الكود وحذفه عند الإبطال/التحقق/انتهاء الصلاحية والتوقف. الاختبارات تستخدم sender في الذاكرة من test composition، ولا تستدعي صندوق التطوير.

```csharp
public partial class Program
{
    public static async Task Main(string[] args)
    {
        var builder = ApiConfiguration.CreateBuilder(args);

        builder.AddApiServices();
        builder.AddApplicationModules();

        var app = builder.Build();

        app.UseApiPipeline();
        app.MapApiEndpoints();

        await app.RunAsync();
    }
}
```

هذا مثال للشكل المطلوب، وليس كودًا منفذًا. تظل startup validation وsafe logging وGET/HEAD health وcorrelation/no-store وProblemDetails من S01 محفوظة. `Program` متاحة لـ`WebApplicationFactory<Program>`، وبقية Host types داخلية افتراضيًا.

`ApplicationModuleRegistration` واستدعاءاتها تدخل عند أول ربط مستخدم لـIdentityAccess؛ لا تنشأ كملف فارغ في تاسك إعادة التنظيم. Business entities/rules وEF mappings وMigrations لا تنتقل إلى Host.

## 6. BuildingBlocks وحدود الموديول

`src/EduCenterOS.BuildingBlocks/` مشروع صغير مستقل للمفاهيم التقنية المستخدمة في السبرنت:

| المكون | الحاجة الحالية |
| --- | --- |
| `IClock` و`SystemClock` | مصدر UTC موحد للانتهاء وإعادة الإرسال؛ `TestClock` داخل الاختبارات. |
| `Result` و`Result<T>` | Success/expected failure؛ لا Error في النجاح ولا Value في الفشل. |
| `Error` و`ErrorCategory` | كود وتصنيف ووصف client-safe، مستقلة عن HTTP. |
| `ValidationIssue` وما يلزم من typed safe metadata | أخطاء حقول bounded وفق T32، دون قيم حساسة أو EF/Exception objects. |

Error/Result factories تمنع الحالات المتناقضة. Module-specific errors تظل في IdentityAccess؛ transport mapping وProblemDetails تظل في API layer. API source prefixes لا تدخل member paths داخل Application.

لا نضيف Entity/AggregateRoot/DomainEvent/transaction/event abstractions إلا إذا ظهر استخدامها الحقيقي في تنفيذ النطاق؛ لا base timestamps أو automatic ID generation لكل entities، ولا generic repositories أو إطار CQRS/Event Bus مبكر.

```text
EduCenterOS.Api → EduCenterOS.Modules.IdentityAccess
EduCenterOS.Api → EduCenterOS.BuildingBlocks
EduCenterOS.Modules.IdentityAccess → EduCenterOS.BuildingBlocks
EduCenterOS.BuildingBlocks → No Business Module / Api dependency
```

الموديول مشروع واحد وفق T04، يحتوي Domain/Features/Infrastructure/Contracts حسب الاستخدام. Default visibility هي `internal`، وpublic registration/contracts بالقدر اللازم فقط.

التخزين داخل نفس physical PostgreSQL database، بـ`identity_access` وDbContext/history مملوكتين للموديول. أول جداول الـFeature: `person_identities` و`user_accounts` و`otp_challenges`؛ rolling counters أو state مساندة تضاف فقط عند الحاجة الفعلية لحماية الفلو، دون جداول جلسات/MFA مستقبلية.

### S02-T03 — BuildingBlocks وموديول IdentityAccess والتخزين

### S02-T05 — OTP وإثبات توثيق الرقم

**الهدف:** مسار طلب/إعادة إرسال/تأكيد الكود وإصدار proof قابل للاستخدام مرة واحدة.

**النطاق:** Vertical Slices للعمليات المذكورة؛ HMAC/version/binding؛ lifecycle والـatomic attempts؛ active-challenge arbitration؛ delivery failure semantics؛ raw proof return once؛ endpoint policies/validation/error mapping وOpenAPI الخاصة بما نفذ.

**المراجع:** T05/T11/T12/T15/T16/T17/T31/T32/T33/T35/T36، وعقود T02.

**معايير القبول:**

2. OTP generated/hashed safely، verification constant-time، ولا raw OTP/proof في DB أو logs/URLs/error metadata.

4. resend يبطل القديم ويحترم minimum interval وrolling limits؛ simultaneous issue/resend لا تترك أكثر من challenge قابلة للاستخدام لنفس target/purpose.
5. failed verification attempt counters atomic؛ simultaneous verify لا تنتج نجاحين/proofs متعددة لنفس challenge.
6. proof secret عالية الـentropy وبصمة فقط في التخزين، lifetime/binding واضحان، ولا تصدر بعد failure أو invalidation.

**التحقق:** Unit lifecycle/HMAC/normalization/boundaries؛ HTTP/PG request/resend/verify/abuse/fault scenarios؛ deterministic concurrent issue/verify مع barriers وseparate scopes/connections وفحص final DB state؛ safe output scans.

### S02-T06 — التسجيل الذري

**الهدف:** إنشاء الحساب والشخص من رقم موثق مع استهلاك proof في نفس Commit.

**النطاق:** RegisterAccount Vertical Slice؛ input/password validation؛ IPasswordHasher<UserAccount> باستخدام security primitive المعتمدة؛ normalized uniqueness؛ UUID v7؛ proof validation/consumption؛ transaction/error handling وHTTP contract/OpenAPI المنطبق.

**المراجع:** Business 02/14، T06/T10/T11/T12/T15/T16/T17/T31/T32/T33/T35.

**معايير القبول:**

1. لا تسجيل دون challenge/proof صالحين للتسجيل ومربوطين بنفس target؛ الموبايل مصدره verified challenge.

**التحقق:** HTTP → production handler → actual PostgreSQL → safe response؛ duplicate/concurrent proof/phone/email races؛ controlled rollback/fault tests وفحص account/person/proof rows؛ password verification دون عرض hash/secret؛ no unexpected business artifacts.
