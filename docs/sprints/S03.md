## 1. الهدف والنتيجة العملية

إكمال فلو إنشاء الحساب في S02 بتسجيل دخول حقيقي وإدارة جلسات من خلال API، داخل `IdentityAccess` الحالية، فوق قواعد Supabase المعتمدة.

عند اكتمال السبرنت يستطيع المطور:

1. إنشاء حساب وتوثيق موبايله بالفلو الحالي، دون تسجيل دخول تلقائي.
2. الدخول بالموبايل وكلمة المرور، واستلام Access JWT قصيرة العمر و Refresh Credential داخل Cookie محمية.
3. استخدام الـ Access Token للوصول إلى بيانات حسابه وجلساته عبر مسارات محمية.
4. تجديد Access Token بتدوير Refresh Credential مرة واحدة لكل استخدام ناجح.
5. عرض جلساته وإبطال جلسة محددة أو الحالية أو كل الجلسات القائمة.
6. إثبات رفض JWT بعد إبطال جلستها، حتى لو توقيعها صحيح ولم تنتهِ صلاحيتها الزمنية.
7. تشغيل وتجربة الفلو من نسخة جديدة، مع فحوصات محلية و CI وأدلة تسليم موثقة.

النتيجة تخص Development و Testing، وليست نشرًا إلى Production. لا تمنح جلسة الدخول عضوية أو Role أو Permission داخل مؤسسة. المسارات المنفذة تخص حساب المستخدم نفسه فقط.

## 5. الفلو التفصيلي

### 5.1 Login

```text
Browser POST login over HTTPS with approved origin/header
  → strict bounded JSON validation and canonical phone normalization
  → identifier/source abuse checks, including unknown accounts
  → resolve account credential snapshot
  → real password verification or equivalent dummy verification
  → on failure: atomic failure state update, generic public rejection
  → on success: begin transaction and lock UserAccount
  → re-check status/lockout/password/security snapshot
  → reset account failure state; optional approved password rehash
  → create PrimaryAuthenticated UserSession
  → generate high-entropy refresh; persist hash only
  → create RefreshTokenRecord bound to session
  → prepare bounded signed access token
  → commit
  → return access JSON and set secure refresh cookie; no-store
```

- Heavy password verification خارج open transaction وفق T16. بعد Account lock لا تعتمد نتيجة مبنية على hash/security snapshot قديمة؛ bounded re-evaluation أو safe failure دون blind retry.
- Unknown/Wrong Password/Unverified Target/Temporary Lock/Suspended/Closed لها public failure موحدة؛ لا disclosure للحالة أوعدد المحاولات أووقت lockout الحساب.
- Input shape errors مستقلة عن وجود الحساب، ولا تعيد كلمة المرور أوالموبايل ك submitted value.
- Password rehash عند `SuccessRehashNeeded` لا يغير `PasswordChangedAtUtc` أو `SecurityVersion` لأنه maintenance.
- لا Tokens أو Set-Cookie تصل قبل Commit. فشل persistence لا يترك Session جزئية أو credential قابلة للاستخدام أُعلن نجاحها.
- Logout all لا يمنع Login جديدة مكتملة بعده؛ لا يساوي Security Reset.

### 5.2 Protected Request

```text
Authorization: Bearer access-token
  → validate signature/RS256/typ/known kid/issuer/audience/lifetime
  → validate every required claim and identifier shape
  → load authoritative account/session state
  → require active account, matching ownership/security versions
  → require non-revoked, unexpired session
  → expose small current actor to handler
  → execute own-account operation only
```

- Valid signature ليست كافية. `sub/sid/sv` يجب أن تطابق Account/Session الحالية.
- لا authorization أو account status أو MFA evidence authoritative من JWT.
- لا sliding idle timeout أو `LastSeenAtUtc` write لكل API request؛ successful Refresh هي activity في هذه السبرنت.
- فقدان DB المطلوبة لا ينتج authenticated actor أو generic invalid-password outcome؛ infrastructure failure آمنة وفق T32، دون السماح بالوصول.
- الإبطال يؤثر في الطلب التالي بعد Commit. لا تدعي الخطة إلغاء response لطلب قرأ الحالة قبل الإبطال؛ mutation تستخدم authoritative recheck داخل transaction المناسبة.

### 5.3 Refresh

```text
Browser POST refresh with cookie + approved origin/header
  → reject invalid CSRF/transport before side effects
  → hash raw refresh in memory; lookup candidate IDs
  → begin transaction
  → lock UserAccount → UserSession → RefreshTokenRecord
  → re-check account/session/security version/record lifetimes
  → if consumed: revoke owning session under reuse policy
  → otherwise: consume A, create B, link lineage
  → update LastSeenAtUtc and bounded idle deadline
  → commit
  → on success: set replacement cookie B + return new access JWT
```

كل rotation تحفظ consumption/replacement/lineage/activity/deadlines في transaction واحدة. عمر Refresh الجديدة لا يتجاوز effective Session expiration، ولا تتحرك absolute lifetime.

Reuse يبطل Session كلها ويجعل كل credentials و JWT المرتبطة بها غير قابلة للاستخدام. **لا grace period**، ولا إعادة raw replacement من cache أو generic idempotency record. طلبان متزامنان بـ A قد ينتجان rotation أولى ثم reuse revocation؛ المعيار هو ألا تبقى descendants صالحة بعد الإبطال.

لو Commit نجحت وضاع الرد، إعادة A تبطل Session وتحتاج Login جديدة. الـ Client يلزمها single-flight refresh؛ لا تلقائية replay عند timeout أو ambiguous commit.

### 5.4 Session management و Logout

```text
List sessions
  → validate bearer/current account
  → paginated account-owned projection; no secrets

Revoke specific session
  → validate current actor and target ownership
  → lock/re-check authoritative state
  → terminal session revocation; already-revoked owned session is no-op

Logout current
  → validate browser origin/header
  → resolve current refresh/session without requiring a live access JWT
  → revoke session if identifiable; absent/invalid cookie is safe no-op
  → expire local refresh cookie with matching attributes

Logout all
  → validate bearer/current actor and browser request controls
  → lock UserAccount then owned UserSessions ordered by Id
  → revoke all sessions existing at the transaction boundary
  → commit without changing SecurityVersion
  → expire current browser refresh cookie
```

Logout current تظل قابلة للاستخدام بعد انتهاء Access JWT. Cookie deletion ليست source of truth؛ `RevokedAtUtc` Server-side هي الأساس. إبطال Session نهائي، ولا يعاد تفعيلها؛ Login جديدة تنشئ ID جديدة.

الأسماء والـ allowlists أدناه هي baseline التخطيط؛ T01 تثبت contract كاملة في `docs/contracts/S03-authentication.md` قبل handlers. لا تعيد تسمية أوكسر S02 routes ضمن هذه السبرنت.

| العملية | Method / Route | الحماية | النتيجة المخططة |
| --- | --- | --- | --- |
| Login | `POST /api/v1/auth/login` | AnonymousSecurity؛ HTTPS و origin/header و abuse controls. | `200` access DTO + refresh Set-Cookie؛ failure موحدة. |
| Refresh | `POST /api/v1/auth/refresh` | AnonymousSecurity؛ refresh cookie و CSRF controls؛ لا Bearer مطلوب. | `200` access DTO + replacement Cookie بعد Commit. |
| Logout current | `POST /api/v1/auth/logout` | AnonymousSecurity؛ cookie-specific protocol و CSRF؛ لا Bearer مطلوب. | `204` بعد revocation/no-op وحذف Cookie؛ DB failure لا توصف كنجاح. |
| Logout all | `POST /api/v1/auth/logout-all` | AccountSelf؛ valid Bearer و browser guards. | `204` بعد الإبطال الذري وحذف Cookie الحالية. |
| Current account | `GET /api/v1/accounts/me` | AccountSelf؛ valid Bearer. | `200` own-account DTO allowlist. |
| List sessions | `GET /api/v1/auth/sessions` | AccountSelf؛ valid Bearer. | `200` paginated own-session DTOs. |
| Revoke session | `POST /api/v1/auth/sessions/{sessionId}/revoke` | AccountSelf؛ valid Bearer؛ ownership و browser guards عند استخدام Cookie. | `204` owned revocation/no-op؛ unknown/foreign target hidden `404`. |

### الطلبات والردود

- Login body: `phoneNumber` و `password` فقط؛ لا account ID أو role أو institution أو session assurance من Client. أي display metadata اختيارية تحتاج allowlist وحدود وتجربة XSS قبل إدخالها في T01.
- Refresh/Logout commands تستخدم body ثابتة مثل `{}` عند الحاجة إلى JSON؛ raw Refresh لا تقبل من body/query/header بديل أو URL.
- Access response allowlist: `accessToken`، `tokenType = Bearer`، `expiresAtUtc`. Session ID المعروضة تأتي من server، وتثبت إضافتها إن احتاجها contract؛ لا Refresh JSON.
- Current account allowlist: `userAccountId`، `personIdentityId`، `fullName`، `createdAtUtc`. لا password/hash، ولا security counters/keys، ولا PII إضافية بلا use-case. الاسم projection من PersonIdentity المملوكة لنفس module.
- Session list allowlist: `sessionId`، `createdAtUtc`، `authenticatedAtUtc`، `lastSeenAtUtc`، `idleExpiresAtUtc`، `absoluteExpiresAtUtc`، `revokedAtUtc`، `isCurrent`. لا refresh hash/raw credential، ولا raw IP/User-Agent.
- Session list تشمل تاريخ الجلسات القائمة والمنتهية والمبطلة دون سياسة purge جديدة. Page contract من T31: `page=1`، `pageSize=20`، maximum `100`، total order بـ `createdAtUtc DESC, id DESC`، envelope المعتمدة. لا cursor في S03؛ لا Data Protection key ring بلا استخدام فعلي.
- Strict JSON/UUID/bounds ورفض unknown mutation fields وفق T31/T32؛ validation paths `body.*`/`route.*`/`query.*`، دون submitted secrets. SessionId ليست permission.
- Protected `401` تحمل `WWW-Authenticate: Bearer` و ProblemDetails موحدة دون token failure internals. T01 تثبت public Login/Refresh challenge mapping وأكواد الأخطاء ونصوصها والحدود التي لا تكشف account state.
- `400` لل shape، `403` ل origin/CSRF denial حسب العقد، `404` لل target المخفية، `429` لل abuse مع `Retry-After` حيث تنطبق. Provider/DB/commit ambiguity وفق T32، ولا تتحول إلى wrong password أو success.
- Sensitive responses والـ errors تستخدم `Cache-Control: no-store`. Generic idempotency لا تحفظ ولا تعيد Login/Refresh credentials أو Set-Cookie.

### Cookie و CORS و CSRF

```text
Name: __Secure-educenteros-refresh
Domain: omitted (host-only)
Path: /api/v1/auth
HttpOnly: true
Secure: true
SameSite: Strict
Expires/Max-Age: no later than refresh record expiration
Business API transport: Authorization: Bearer only
```

Path تغطي Refresh و Logout current/all؛ ليست access boundary. الإصدار والحذف يستخدمان Name/Path/Domain policy نفسها و compatible Secure/SameSite attributes.

- same-site first-party browser فقط، مع exact origin مقارنة scheme/host/port؛ لا suffix matching أو `Origin: null` أو missing Origin على browser commands المشمولة.
- Required non-simple custom header مثل `X-EduCenterOS-Auth` تثبت قيمتها في T01؛ CORS allowlist صريحة لل methods/headers و credentials عند الحاجة، بلا `AllowAnyOrigin + AllowCredentials`.
- JSON فقط لل security commands؛ رفض simple form/text content types، و POST فقط، و preflight لا يغير state أو يكشف secrets.
- Origin/header defenses تطبق على Login أيضًا لأنه يصدر Cookie، إضافة إلى Refresh و Browser Logout. SameSite ليست بديلًا عنها.
- Access في browser memory فقط؛ لا localStorage/sessionStorage/IndexedDB أو Swagger persisted authorization. التشغيل الفعلي يثبت cookie jar و Origin behavior؛ server-side HTTP client وحدها لا تثبت browser SameSite/CORS enforcement.

## 7. JWT و Session و Persistence invariants

### JWT profile

```text
alg = RS256 only
typ = educenteros-access+jwt exactly
kid = known configured local public key
Claims allowlist = iss, aud, sub, sid, jti, iat, exp, sv
MapInboundClaims = false
SaveToken = false
IncludeErrorDetails = false
```

Issuer/audience/signature/lifetime كلها validated. Required claims missing/malformed، `Guid.Empty` identifiers، invalid security-version representation، `exp <= iat`، wrong typ/alg، unknown kid تفشل. لا `jku/x5u` remote discovery أو fallback key. لا `nbf` إصدار ضمن profile الحالية.

RSA private PEM >=2048 bits، current kid تطابق public validation member و private/public material. Key rotation: prepublish public key → activate signing → retain previous validation key حتى آخر token expiry + configured skew → retire؛ لا reuse version ID بمادة مختلفة.

```text
JWT.sv == Session.SecurityVersionAtAuthentication == Account.SecurityVersion
AccessExpiresAtUtc <= min(now + AccessLifetime, SessionEffectiveExpiration)
SessionEffectiveExpiration = min(IdleExpiresAtUtc, AbsoluteExpiresAtUtc)
Session expired when nowUtc >= either deadline
RefreshRecord.ExpiresAtUtc <= SessionEffectiveExpiration
```

Clock skew الخاصة بال JWT لا تمدد صلاحية Session Server-side. JWT NumericDate تقاس بدقة الثواني؛ PostgreSQL round-trip بالدقة الفعلية؛ الاختبارات لا تفترض تحكم IClock في framework clocks تلقائيًا.

### Domain و EF

- `UserSession` و `RefreshTokenRecord` و Domain transitions داخل IdentityAccess، مع UUID v7/UTC و Version منفصلة عن SecurityVersion.
- UserAccount FK في session، و session FK في refresh، و replacement self-FK، و unique token hash، و check constraints للعمر/القيم حيث يمكن التعبير عنها.
- Refresh secret: CSPRNG 32 random bytes، Base64Url transport، SHA-256 hash في DB فقط. Lineage لا تسمح باستهلاك مزدوج أو replacement fork.
- Indexes ل account-owned session pagination، lookup بـ hash، و session credential history؛ no global query أو unbounded scan.
- Sessions وال refreshs والمطلوب من login abuse state فقط؛ لا جداول MFA/Institutions مستقبلية. Policies ليست constants موزعة في Domain.
- Migration upgrade من S02 القائمة تحفظ account/OTP/rate state؛ development migrations عبر migrator منفصل، لا startup DDL أو admin credentials في API.
- Locks عند الحاجة: `UserAccount → UserSession rows ordered by Id → Credential rows ordered by Id`. Candidate lookups لا تغني عن authoritative reload داخل transaction.
- Reuse revocation نفسها durable قبل إعلان نتيجتها؛ DB outage لا تسمح بتجديد أوتجاهل reuse.
- Login/Refresh/Logout/revoke/logout-all لها commit-all/rollback-all tests؛ unknown commit لا يعاد عميانيًا. SecuritySpecific flows لا تدخل generic T17 credential replay.

### قواعد تنفيذ الاختبارات

- Security tests تستخدم production issuance/validation و real HTTP pipeline بـ runtime-generated test keys؛ لا Test Auth scheme بديل لإثبات أمان المصادقة.
- Unit/Architecture دون DB credentials. Integration على Supabase Testing فقط؛ marker/role/TLS/server-major/lease checks قبل reset/cleanup وفق T41.

- Time boundaries تختبر بساعة محكومة وفق representation precision. Framework clocks تستخدم supported seam أو valid/expired cases بعيدًا عن boundary عند غيابها؛ لا bypass لـ JWT lifetime validation.
- Failure قبل Commit منفصلة عن actual Commit ثم response loss. DB assertions من fresh authoritative context؛ لا shared tracked entities أو fake committed flag.
- State transitions المؤجلة تستخدم test-only owned fixture في Testing boundary وبـ lock/security protocol الصحيح عند race؛ لا API backdoor أو Feature lifecycle مبكرة.
- Raw password/PEM/JWT/Refresh/Cookie/OTP/proof لا تدخل test names/assert failure text/stdout/published artifacts؛ published evidence تظل safe allowlist فقط.
- Missing credentials/DB/discovery أو skipped required tests ليست نجاحًا؛ لا assert removal أو automatic rerun لإخفاء failure. MFA/Institutions غير المنفذة لا تضاف كـ skipped tests.
