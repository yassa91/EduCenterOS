# T40 - Git & GitHub Workflow

## حالة القرار والهدف

```text
Status: Approved
Approved on: 2026-10-01
Scope: Sprint planning, task delivery, Git and GitHub collaboration
```

تثبيت طريقة العمل طوال المشروع: نتفق على نتيجة السبرنت ومحتواه قبل التنفيذ، وننفذ كل Task متماسكة في Branch مستقلة، ثم نراجع ونفحص وندمج من خلال Pull Request.

اعتماد هذا الملف اعتماد لطريقة العمل؛ لا يعني أن Git repository أو GitHub repository أو branch protection أو CI تم إعدادها بالفعل.

---

## 1. القرار المعتمد

```text
Agreed sprint outcome and scope
    → documented sprint and ordered tasks
    → task branch from latest main
    → implementation and verification
    → Pull Request and review
    → Squash and Merge into main
    → branch cleanup and sprint task update
    → next task from updated main
```

نعتمد GitHub Flow مع `main` كفرع التكامل الأساسي. التنفيذ المعتاد للتاسكات متتابع حسب ترتيب واعتماديات السبرنت المعتمد.

كل Task تمثل تغييرًا متماسكًا يمكن مراجعته ودمجه. الخطوات الصغيرة التي لا تكتمل إلا معًا تكون Subtasks داخل نفس Task ونفس Branch.

---

## 2. التفويض بالدمج

فوّض صاحب المشروع المساعد بتنفيذ دورة GitHub الخاصة بالتاسكات المتفق عليها، بما يشمل Commit وPush وإنشاء Pull Request ومعالجة ملاحظات المراجعة والدمج وحذف Branch التاسك بعد الدمج.

**لا يحتاج المساعد موافقة جديدة على كل PR عندما تكتمل معايير القبول والفحوصات والمراجعة المحددة في هذا الملف والتاسك المعتمدة.**

التفويض مستمر إلى أن يغيّره صاحب المشروع. لا تعتبر إضافة نطاق جديد أو تغيير Business/Technical Decision ضمنيًا جزءًا من تفويض الدمج؛ تغيير النطاق يخضع لاتفاق السبرنت في القسم التالي. النشر إلى Production له اتفاقه المستقل.

لو ظهرت مشكلة تمنع استيفاء شروط الدمج، يعالجها المساعد داخل نطاق التاسك. إذا احتاج حلها قرارًا من صاحب المشروع، يوضح القرار المطلوب ويترك PR غير مدمجة حتى حسمه.

---

## 3. الاتفاق على السبرنت قبل التنفيذ

قبل بدء السبرنت نتفق على:

- الهدف والنتيجة العملية التي ستكون متاحة عند اكتماله.
- النطاق الداخل في السبرنت وما تم تأجيله.
- التاسكات وأرقامها وترتيبها واعتمادياتها.
- معايير قبول كل Task وكيفية التحقق منها.
- أي Business أو Technical Decisions مطلوبة لتنفيذ النطاق.

بعد الاتفاق ينشأ ملف السبرنت في:

```text
docs/sprints/S01.md
docs/sprints/S02.md
```

يحتوي الملف على الهدف والنتيجة والنطاق والتاسكات والتفاصيل السابقة، مع حالة كل Task وروابط PR ونتائج التحقق وملاحظات الإغلاق.

تفاصيل كل Task تشمل:

| Field | المحتوى |
| --- | --- |
| ID | معرف مثل `S01-T03` |
| Goal | التغيير المطلوب والغرض منه |
| Scope | حدود العمل المتفق عليه |
| Dependencies | التاسكات والقرارات التي تعتمد عليها |
| References | مصادر Business وTechnical ذات الصلة |
| Acceptance Criteria | شروط واضحة تثبت اكتمالها |
| Verification | الفحوصات والاختبارات المناسبة |
| Status | الحالة الحالية |
| Delivery | Branch وPR ونتيجة الدمج |

حالات التاسكات المعتمدة:

```text
Planned → In Progress → In Review → Done
Blocked: يتطلب قرارًا أو اعتمادًا غير متاح، مع توثيق السبب
```

هذه حالات التنفيذ في ملف السبرنت. سجل Business 16 يظل سجل حالة القرارات ولا يستخدم لتتبع تقدم الكود.

أي تغيير يؤثر على هدف السبرنت أو نطاقه أو معايير قبوله يناقش مع صاحب المشروع ويحدث في الملف بعد الاتفاق، قبل تنفيذ العمل المضاف. تفاصيل التنفيذ المعتادة داخل النطاق تحسم وفق القرارات المعتمدة دون طلب موافقة على كل خطوة.

---

## 4. إنشاء Branch التاسك

قبل إنشاء Branch:

1. نتأكد أن تغييرات العمل الحالية محفوظة ومنسوبة للتاسك الصحيحة.
2. نحدث `main` من GitHub دون الكتابة فوق تغييرات محلية أو تغييرات صاحب المشروع.
3. ننشئ Branch جديدة من أحدث `main` للتاسك التالية الجاهزة وفق الاعتماديات.

صيغة الاسم:

```text
<type>/<sprint-task-id>-<short-description>
```

أمثلة:

```text
feat/s01-t03-api-host
fix/s02-t04-login-validation
docs/s01-t01-workflow
chore/s01-t02-solution-setup
test/s02-t05-tenant-isolation
```

الاسم lowercase ووصفه مختصر. نوع التاسك يصف تغييرها الأساسي؛ الاختبارات والتوثيق اللازمة لنفس التغيير تبقى في نفس Branch.

لا يعاد استخدام Branch بعد دمجها. التاسك الجديدة تبدأ من `main` المحدثة.

---

## 5. التنفيذ والـCommits

- كل Branch تقتصر على Task المعتمدة وإصلاحاتها اللازمة.
- الـCommits واضحة وتحفظ خطوات مفهومة من العمل.
- صيغة الرسالة: `<type>: <description> [<task-id>]`، مثل `feat: add API host [S01-T03]`.
- نحدث التوثيق عندما يتغير سلوك موثق أو إعداد تشغيل يخص التاسك.
- نلتزم بـT33 للاختبارات المناسبة للتغيير، وT35/T36 للأمان والأسرار.
- لا نسجل Secrets أو بيانات حقيقية حساسة أو ملفات تشغيل مؤقتة ضمن التغييرات.
- التغييرات على `main` بعد تهيئة المستودع تمر عبر PR؛ لا Direct Push أو Force Push إلى `main` ولا تجاوز لحمايتها.

---

## 6. Pull Request والمراجعة

كل Task لها PR تستهدف `main`. يمكن فتح Draft أثناء العمل، وتصبح جاهزة للمراجعة عندما يكتمل التنفيذ والفحص.

عنوان PR يصف النتيجة ويحتوي Task ID. الوصف يشمل:

- المشكلة أو الهدف والسلوك الناتج.
- أهم التغييرات التي يحتاج المراجع فهمها.
- Task ID ومرجع ملف السبرنت.
- الفحوصات التي شغلت فعلًا ونتائجها.
- أي قيود أو قرارات يحتاج المراجع معرفتها.

المراجعة تتحقق من مطابقة معايير القبول والقرارات المعتمدة، وصحة السلوك وحدود الموديولات، وكفاية التحقق، وعدم إدخال تغييرات غير مرتبطة بالتاسك.

يراجع المساعد التغيير النهائي ويعالج الملاحظات قبل الدمج. إذا كانت إعدادات المستودع تتطلب Approval من مراجع آخر، يجب استيفاؤها؛ مراجعة المساعد لا تستبدل GitHub Approval مطلوبة، ولا توصف بأنها مراجعة مستقلة.

أي تعديل بعد المراجعة يعاد فحصه ومراجعته بالقدر الذي يتأثر به. لا تعلن نتائج أو مراجعة لم تحدث فعلًا.

---

## 7. شروط الدمج وDefinition of Done

يسمح بالدمج عندما:

1. اكتمل نطاق التاسك ومعايير قبولها.
2. نجح Build والفحوصات والاختبارات المطلوبة والمنطبقة على التغيير وفق التاسك وT33.
3. نجحت Required Status Checks وRequired Approvals المفعلة على GitHub.
4. اكتملت مراجعة النسخة النهائية وعولجت ملاحظاتها المانعة للدمج.
5. لا توجد Merge Conflicts، والتحقق يغطي الحالة التي ستدمج مع `main` الحالية.
6. التوثيق المطلوب ونتائج التحقق موجودة وقابلة للمراجعة.

فشل فحص مطلوب أو عدم القدرة على تشغيله لا يعتبر نجاحًا؛ لا يعطل شرط مطلوب لتسهيل الدمج. قبل تجهيز CI توثق الفحوصات المحلية المنفذة، ولا يدعى أن CI نجحت. تفاصيل تجهيز CI نفسها تتبع T38 عند اعتمادها وتنفيذها.

بعد اكتمال الشروط يستخدم **Squash and Merge**: تصبح تغييرات PR Commit واحدة على `main` بعنوان يصف التاسك ويحتوي معرفها. تفاصيل العمل والمراجعة تبقى في PR.

بعد الدمج:

- نتأكد من نجاح الدمج ونسجل رابط PR ونتيجة التحقق في ملف السبرنت.
- نحذف Branch التاسك من GitHub وننظف Branch المحلية عندما تكون مدمجة وخالية من عمل غير محفوظ.
- نحدث `main` ونضع التاسك `Done` بعد اكتمال سجل تسليمها.
- نبدأ التاسك التالية من `main` المحدثة.

تحديث سجل السبرنت الخاص بالدمج يتم ضمن PR التالية أو PR توثيق صغيرة عند الحاجة، بنفس قواعد المراجعة والدمج؛ لا نستخدم Direct Push إلى `main` لهذا التحديث.

---

## 8. إعداد المستودع والتعارضات والتراجع

عند تهيئة GitHub نفعل Squash Merge وقواعد حماية `main` والفحوصات المطلوبة التي تم تجهيزها فعلًا، وفق الإمكانات المتاحة. نسجل ما تم تفعيله، ولا ندعي وجود حماية غير مفعلة.

تهيئة المستودع والـinitial commit خطوة تأسيسية تسبق دورة PR المعتادة؛ بعدها ينطبق مسار Branch → PR → Merge على تغييرات المشروع.

تعالج Merge Conflicts داخل Branch التاسك مع الحفاظ على قصد التغييرين، ثم يعاد الفحص والمراجعة على النتيجة. التعارض الذي يتضمن Business Decision غير محسومة يتطلب حسم القرار قبل الدمج.

إذا لزم التراجع عن تغيير مدمج، نستخدم Revert في Branch جديدة ومن خلال PR موثقة، ثم نفحصها ونراجعها. لا نعيد كتابة تاريخ `main`. أي إصلاح أو تراجع يحدث معه سجل السبرنت المتأثر.

---

## 9. إغلاق السبرنت

نراجع النتيجة الفعلية مقابل الهدف ومعايير القبول المتفق عليها، ونسجل:

- ما أصبح قابلًا للتشغيل أو الاستخدام بالفعل.
- التاسكات المكتملة وروابط PR ونتائج التحقق.
- أي عمل لم يكتمل وسببه وتأثيره على النتيجة.
- القرارات أو الاعتماديات المطلوبة للمرحلة التالية.

إغلاق الفترة أو الانتقال لسبرنت جديدة لا يجعل Task غير مكتملة `Done`. ترحيلها أو تعديل النطاق يحتاج اتفاقًا وتحديثًا واضحًا في ملفات السبرنت.
