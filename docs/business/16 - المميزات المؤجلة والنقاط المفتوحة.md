# 16 - المميزات المؤجلة والنقاط المفتوحة

## Decision Register

```text
Document Type: Business Decision Register
Status: Approved Baseline
Scope: EduCenterOS Business Specification 00–15
```

---

# 1. هدف الملف

الملف ده هو **السجل المركزي لحالة القرارات** في EduCenterOS.

وظيفته الأساسية إنه يجاوب عن:

> هل النقطة دي محسومة؟

> هل هي محسومة لكن مؤجلة؟

> هل لسه محتاجة قرار؟

> هل عندنا اتجاه مبدئي لكن لازم نتحقق منه قبل التنفيذ أو Production؟

الملف لا يعيد شرح الـBusiness Rules بالتفصيل.

التفاصيل تظل داخل Source File المتخصص.

---

# 2. الملف لا يتابع حالة الكود

هذا الملف لا يستخدم حالات مثل:

```text
Implemented
In Progress
Sprint 03
Not Started
```

لأن دي Implementation / Project Management Status.

`16` يتابع:

> **حالة القرار نفسه.**

وبالتالي:

```text
DECIDED
```

لا تعني إن Feature اتبرمجت.

تعني فقط:

> الفريق مش محتاج يخترع Business Decision جديدة بشأن النقطة دي.

---

# 3. حالات القرارات

نعتمد أربع حالات فقط.

| Status | المعنى |
|---|---|
| `DECIDED` | القرار محسوم ومصدر الحقيقة موجود في ملف متخصص. |
| `DEFERRED` | الاتجاه معروف بدرجة كافية، لكن التنفيذ خارج النطاق الحالي عمدًا. |
| `OPEN` | توجد نقطة Business مؤثرة لم يتم حسمها، ولا يجوز اختراع Behavior أثناء التنفيذ. |
| `NEEDS_VALIDATION` | يوجد Baseline أو اتجاه مبدئي، لكنه يحتاج تحققًا تجاريًا أو قانونيًا أو تشغيليًا أو أمنيًا قبل اعتماده للإنتاج. |

---

# 4. الفرق بين `DEFERRED` و`OPEN`

دي من أهم قواعد الملف.

## `DEFERRED`

يعني:

> عارفين إحنا عايزين إيه تقريبًا، لكن مش هنعمله دلوقتي.

مثال:

```text
QR Attendance
```

مش مطلوب في Core V1.

ده لا يمنع تنفيذ Attendance العادية.

---

## `OPEN`

يعني:

> لو هننفذ الجزء المتأثر دلوقتي، لازم ناخد قرار الأول.

مثال:

لو النظام هيفحص تعارض جدول الطالب، لكن لسه ما حسمناش:

```text
Warning
or
Blocking Rule
```

فالـDeveloper ما يختارش واحدة من نفسه.

---

# 5. معنى `NEEDS_VALIDATION`

تعني إن عندنا اتجاه معقول، لكن الوثيقة وحدها لا تكفي لاعتماده نهائيًا.

مثل:

- سعر Plan.
- Trial duration.
- Legal age threshold.
- Refund window.
- Data retention legal period.
- Payment provider.
- RPO/RTO.

الـDeveloper لا يحول الأرقام المبدئية إلى Constants دائمة كأنها حقيقة نهائية.

---

# 6. مصدر الحقيقة

ترتيب المرجعية:

```text
Specialized Business File
        ↓
Decision Register 16
        ↓
Architecture / Data / API Decisions
        ↓
Implementation
```

`16` لا يغير Rule موجودة في Source File.

هو فقط يسجل:

- الحالة.
- المصدر.
- سبب التأجيل/الفتح.
- Dependencies.
- شرط الإغلاق أو الترقية.

# 7. بنية كل Decision

كل قرار يفضل أن يحتوي على:

| Field | المعنى |
|---|---|
| `Decision ID` | معرف ثابت للرجوع للقرار |
| `Topic` | اسم النقطة |
| `Status` | DECIDED / DEFERRED / OPEN / NEEDS_VALIDATION |
| `Owner` | الـDomain المسؤول |
| `Source` | ملف مصدر الحقيقة |
| `Summary` | ملخص قصير فقط |
| `Dependency / Reason` | لماذا الحالة الحالية موجودة |
| `Closure / Promotion Condition` | متى تتغير الحالة |

---

# 8. قاعدة عدم التكرار

لو Rule كاملة موجودة مثلًا في `06`:

لا ننقلها كلها إلى `16`.

نكتب فقط:

```text
FIN-001
Student finance uses ledger-style financial events.
Status: DECIDED
Source: 06
```

ثم نرجع إلى `06` للتفاصيل.

---

# 9. قاعدة تعديل القرار

لو قرار `DECIDED` اتغير:

أول خطوة:

> تعديل Source File المتخصص.

ثم:

> تحديث `16`.

لا يتم تغيير `16` وحده وترك المصدر القديم.

# 40. القاعدة النهائية

`16` لا يشرح النظام.

`00–15` هم اللي بيشرحوا النظام.

`16` يجاوب فقط:

```text
هل القرار محسوم؟
هل مؤجل؟
هل مفتوح؟
هل يحتاج Validation؟
```

والقواعد النهائية هي:

> **`DECIDED` لا تعني Implemented.**

> **`DEFERRED` لا تعني Unknown.**

> **`OPEN` لا تعني إن الـDeveloper حر يختار.**

> **`NEEDS_VALIDATION` لا تعني إن الـBaseline تتحول Hard-coded production rule.**

> **Source Business File هي مصدر الحقيقة، و`16` تسجل حالة القرار فقط.**

> **Feature مؤجلة لا تجبرنا على بناء Schema أو Endpoint أو Abstraction غير مستخدمة الآن.**

> **Marketplace مؤجلة كPhase 2، لكن فصلها عن Core محسوم بالفعل.**

> **القيم التجارية والقانونية والأمنية المتغيرة لا تعامل كConstants أبدية.**

> **أي Rule مفتوحة يجب أن تُحسم قبل تنفيذ الجزء الذي يعتمد عليها، وليس بعد كتابة الكود.**

> **كل قرار Business جديد مهم يجب أن يكون له Owner وSource واضحان.**

الهدف النهائي إن أي عضو في الفريق يقدر يفتح الملف ويعرف فورًا:

> «هل إحنا نسينا النقطة دي؟»

أم:

> «لا، إحنا واخدين قرار بتأجيلها.»

أو:

> «الاتجاه معروف لكن الرقم لسه محتاج Validation.»

أو:

> «دي نقطة مفتوحة فعلًا، وممنوع نختار Behavior من نفسنا.»

وبكده يفضل الفرق واضح بين:

```text
Known
Deferred
Unresolved
Needs validation
```

بدون ما يتحول الملف إلى نسخة ثانية من كل الـBusiness Documentation أو إلى Project Management Board.
