## قبول الـcookie من المتصفح

المضيف المؤقت استخدم production builder/pipeline/modules والـDbContext/migrations الأصلية، وHTTPS من Kestrel بشهادة الجهاز. حمل snapshot Testing كاملة مع RSA صناعية وissuer/origin منفصلين وفق اختبار المشروع، وغيّر OTP sender فقط إلى mailbox محلية محمية. صفحة تشغيل الاختبار مؤقتة ومهملة في Git؛ ليست frontend للمنتج ولا OTP-read API.

1. Request phone verification أعادت challenge من المسار الحقيقي.
2. Verify ثم Register أعادا proof و201؛ GET me دون Bearer رفض، فالتسجيل لا ينشئ جلسة.
3. Login ثم GET me نجحا للحساب نفسه؛ response allowlist تضم Access فقط، وrefresh غائبة عن `document.cookie`.
4. GET me مع cookie المتصفح وحدها ودون Bearer رفض بـ401.
5. Refresh نجحت بcookie jar الأصلية للمتصفح؛ استبدلت الاعتماد وأعادت Access جديدة دون إدخال Cookie يدويًا.
6. قائمة الجلسات أعادت جلسة الحساب الحالية و`isCurrent` الصحيحة.
7. Revoke للجلسة الحالية أعادت 204؛ JWT السابقة وRefresh رُفضتا بعدها.
8. Login جديدة ثم Logout بcookie وحدها نجحت؛ JWT وRefresh رُفضتا بعدها.
9. Login مرتان ثم LogoutAll أبطلتا كلتا الجلستين؛ كلتا JWT رُفضتا بعد Commit.
10. لم تبقَ Refresh قابلة للاستخدام، وlocalStorage/sessionStorage بقيتا فارغتين؛ لم تُعرض credentials/proofs/cookies في الصفحة أو صورة القبول.

أغلق المضيف بعد القبول ونجح cleanup تحت ملكية fixture في schemas الاختبار المعتمدة فقط. فحص read-only أكد صفر holders لقفل الاختبار قبل بدء CI؛ لم تُشغّل Integration محلية بالتوازي مع GitHub على المشروع المشترك. قاعدة Development وحساباتها لم تستقبل بيانات اختبار هذا الفلو.

## مراجعة معايير السبرنت

| المعيار | التحقق |
| --- | --- |
| Login وanti-enumeration وlockout/quotas | Integration تشمل الحساب المجهول/كلمة مرور خاطئة/حالات الحساب والقفل وdummy primitive وrehash وpersistent identifier budgets. |
| JWT/profile/key rotation | production issuance/validation، RS256/typ/kid/issuer/audience/claim allowlists؛ التوقيع/الانتهاء/skew والمفاتيح القديمة/المجهولة وstrict IDs مغطاة. |
| حالة حساب/جلسة authoritative | Protected GET تعيد قراءة الحالة والنسخة الأمنية؛ الإلغاء والانتهاء لا يعتمد على صحة التوقيع وحدها ولا يمدد نشاط الجلسة. |
| Refresh وreuse وCommit ambiguity | rotation/lineage/reuse وexpired ancestor وسباقات PostgreSQL وفشل قبل/بعد Commit وwithholding responses مغطاة؛ لا grace window أو credential replay. |
| Ownership وpagination وlogout | owner-filtered DTOs والترتيب والصفحات الكبيرة وhidden 404 وtarget revoke/current/all وLogin/Refresh overlaps مغطاة. |
| Browser boundary | HTTPS/Origin/header وCORS وSecure/HttpOnly/SameSite/host-only/path/deletion في اختبارات HTTP؛ cookie jar حقيقية مثبتة بالفلو أعلاه. |
| Regression والبنية | OTP/proof/registration/runtime/health/errors/correlation وTLS/roles/lease/report guards وformatter والحدود بين الـfeatures/modules ضمن البوابة. |

المراجعة استخدمت `educenteros-formatting` و`vertical-slice` و`clean-code` و`test-anti-patterns` و`supabase-postgres-best-practices`، مع `systematic-debugging` لتشخيص CI. حارس العمارة لا يفحص كل تعليمات IL، والمراجعة المباشرة تكمله؛ لا يدعى قياس load/throughput أو مراجعة مستقلة.

تدقيق `test-anti-patterns` في متابعة CI محدد بتسعة test methods في `ReportGateTests` وhelpers/مواردها، باستخدام قواعد Python/unittest المدمجة لعدم وجود language-extension محلية. النتيجة: صفر Critical/High/Medium/Low findings؛ assertions فعلية لقرار gate والحقول المسموحة، outcomes مستقلة، specific exception type، ملفات مؤقتة تنظف بالـcontext manager، وsubTests تستخدم توقعات ثابتة دون نشر البيانات الحساسة. التغطية العامة السابقة في CQ01 تبقى موثقة في تقريرها؛ لا يُدعى إعادة تدقيق كل method ضمن هذا الفحص المحدد.
